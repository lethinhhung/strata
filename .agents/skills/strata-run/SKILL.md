# Run Strata

Use Strata's newest `origin/main` build for every requested Strata task. Keep the Strata source/cache outside the target repository; never switch or reset the user's Strata checkout.

## Get the current build

Use a dedicated cache at `${CODEX_HOME:-$HOME/.codex}/cache/strata-main`:

1. If it is not a Git checkout, clone `https://github.com/lethinhhung/strata.git` there.
2. Fetch `origin main`, check out `origin/main` detached, and reset this dedicated cache to `origin/main`. This cache is disposable and must not contain user edits.
3. Reuse dependencies in the cache across runs. Compute a fingerprint from `package.json` and whichever of `package-lock.json` or `npm-shrinkwrap.json` exists. If `node_modules` is missing or the fingerprint differs from the saved `.strata-deps.sha256`, install dependencies: use `npm ci` when the checked out source contains a lockfile, or `npm install` when it does not. Save the new fingerprint after a successful install. A lockfile generated by `npm install` in this disposable cache may be retained for later runs. Then run `npm run build`. If fetching, installing, or building fails, stop and report the error; do not fall back to an older build.
4. Invoke the resulting CLI with `node <cache>/dist/src/cli.js ...`. Do not rely on a globally linked `strata` binary.

## Prepare and run a target repository

Resolve the user's requested repository path, defaulting to the current repository only when the request clearly refers to it. Confirm it is a Git repository on a named branch with a clean worktree before starting a new run; Strata commits and pushes completed stages to that branch. Do not discard changes, change branches, or push manually. If the repository is dirty or detached, explain the prerequisite and ask how to proceed.

If `<repo>/.strata.toml` does not exist, run `strata init --repo <repo>` using the freshly built CLI. Preserve an existing config. Strata's built-in defaults use Codex for coordinators and OpenCode with GPT OSS 20B for workers; check that the configured provider CLIs are available and authenticated before launching.

Start the workflow with either:

- `node <cache>/dist/src/cli.js run "<epic>" --repo <repo>`
- `node <cache>/dist/src/cli.js run --epic <file> --repo <repo>`

An explicit user request to implement/run an epic authorizes starting Strata; its documented stage commits and pushes are part of that workflow. If the user only asks to configure or inspect Strata, do not start a run. Stream and summarize provider progress and the final run ID/status. Strata's CLI runs synchronously; while it is active, relay meaningful progress at reasonable intervals rather than launching duplicate runs.

## Monitor and resume

Inspect saved runs with `node <cache>/dist/src/cli.js status --repo <repo>`. Explain each run's status and identify the newest relevant run when the user has not supplied an ID. Resume an interrupted run with `node <cache>/dist/src/cli.js resume <run-id> --repo <repo>` only when requested or clearly implied by the user's request to continue. Strata stores run records under `<repo>/docs/temps/` and the epic at `<repo>/prompt/epic.md`; use those records to report blockers and progress.

Do not edit run records to fake progress. If a run fails, report the blocker and offer the next concrete action. Preserve completed stages and use Strata's resume command for recovery.
